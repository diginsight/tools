# Evidence dossier schema

**Purpose**: The handoff contract between investigation and authoring — the only artifact an author may read.

## 📍 Location and lifecycle

| Concern | Rule |
|---|---|
| **Path** | `src/docs/_evidence/{component-id}/{area}.md` |
| **Sensitive sibling** | `src/docs/_evidence/{component-id}/{area}.internal.md` |
| **Frontmatter** | both carry `publish: false` |
| **Lifecycle** | regenerated by its investigator, NEVER hand-edited |
| **Read by** | authors (published side only), the verifier, the robustness analyst |
| **Discovery artifact** | `src/docs/_evidence/_discovery.md` (📖 `01-discovery-model.md`) |

Dossiers are **not** documentation. They are never linked from a published page and never appear in navigation.

### The six areas

One dossier per area per component. Areas match the six investigators, so no dossier is unowned and none is written twice.

| Area | Owning investigator | Answers |
|---|---|---|
| `code` | `ad-code-investigator` | what the component does |
| `data` | `ad-data-investigator` | what it persists |
| `configuration` | `ad-configuration-investigator` | what is configurable |
| `environment` | `ad-environment-investigator` | what is provisioned |
| `devops` | `ad-devops-investigator` | how it is built and shipped |
| `security` | `ad-security-investigator` | how it is defended |

## 🧾 Record shape

Every recorded fact carries all six fields. A record missing any of them is incomplete and the verifier rejects pages built on it.

| Field | Content |
|---|---|
| `id` | stable anchor, `{area}-{nn}`, referenced by page traceability anchors |
| `assertion` | the fact, stated as one sentence in the present tense |
| `where` | evidence location — repository path plus symbol or line span, a resource identifier, or a capture asset path |
| `kind` | `source` · `configuration` · `schema` · `live-observation` · `capture` |
| `environment` | which environment the observation came from; omitted for `source` and `configuration` |
| `observed` | ISO date the observation was made |
| `confidence` | `established` · `corroborated` · `claimed` |

### Confidence semantics

| Value | Meaning | Publishable as fact? |
|---|---|---|
| `established` | read directly from the authoritative artifact | ✅ yes |
| `corroborated` | inferred from behaviour and confirmed by a second independent source | ✅ yes, with the inference stated |
| `claimed` | asserted by a README, comment or commit message and **not** corroborated | 🚫 no — publishable only as an attributed claim |

## 🕳️ Gap records

A fact that was **sought and not found** is recorded explicitly.

```markdown
### Gap: {question that could not be answered}

- **Sought**: what fact was needed and which page or finding depends on it
- **Attempted**: each source searched and what it returned
- **Blocked by**: access, absence, or ambiguity
```

An **empty section** ("this area recorded nothing") and a **gap-free section** ("everything asked was found") are opposite signals and MUST be distinguishable. A dossier area with neither records, gaps nor an inapplicability record is itself a defect — it means the investigator did not run.

## 🚫 Inapplicability records

Some areas cannot apply to some components. A component that persists nothing has no `data` area to investigate. Skipping it silently produces a dossier byte-identical to one whose investigator crashed, so inapplicability is **asserted**, never assumed.

### The role-resolution test

An area is inapplicable to a component when **none of the source-set roles its investigator owns resolves to anything that component uses** (📖 `05-source-sets-and-propagation.md`).

Resolution is **not confined to the component's own subtree**. A role that resolves to a location elsewhere in the repository, or outside it through a pointer the repository declares, has resolved — and the area is applicable. Reading "resolves" as "resolves to a path under this folder" would mark an area inapplicable precisely where its evidence is hardest to find.

A repository-level role resolves for a component when it **names or covers** that component. A declared assessment catalogue that lists a component therefore makes `security` applicable to it, whatever the component's own sources show.

This is mechanical and carries no stack assumption: it asks only whether the roles resolve, never what technology the component uses. The same test that makes `data` inapplicable to a documentation-only component makes it applicable to one that gains a schema next week.

```markdown
### Inapplicable: {area}

- **Roles tested**: every source-set role this area owns, listed by name
- **Result**: none resolved to a path inside this component
- **Reason**: one sentence, stated in role terms
- **Observed**: ISO date
```

### What separates the four outcomes

| Situation | Recorded as |
|---|---|
| Roles resolve, facts found | records |
| Roles resolve, facts sought and not found | gap |
| No role resolves | inapplicability record |
| Investigator did not run | **defect** — nothing is recorded at all |

Three rules keep the boundary sharp:

- The investigator **still runs**. It resolves its roles, finds none, and records that result — inapplicability is an output of investigation, not a reason to skip it.
- **One resolving role makes the area applicable.** Partial resolution is applicability with gaps, never inapplicability.
- An area MUST NOT be recorded inapplicable because it found nothing interesting. Roles that resolve to real paths holding no facts produce a **gap**.

## 📋 Coverage declaration

Each dossier opens by declaring which questions its area is responsible for answering, then marks each as answered or gapped. This is what lets the verifier detect a dossier that is **silently incomplete** — one that looks populated because it answered the easy questions.

```markdown
## Coverage

| Question | Status |
|---|---|
| {question owned by this area} | ✅ answered by `code-04` / 🕳️ gap / 🚫 not applicable |
```

An **inapplicable area still declares its full question list**, every entry marked 🚫 not applicable. Dropping the questions would make an inapplicable area look like an unrun one at exactly the point where the difference matters, and would hide the moment a component grows a surface the area now owns.

## 🔐 Sensitive-material split

A fact classified sensitive under 📖 `03-evidence-access-policy.md` is routed to the `.internal.md` sibling.

| Side | Holds | Visible in navigation? |
|---|---|---|
| `{area}.md` | every non-sensitive record; for each sensitive fact, a **redacted stub** | no (`publish: false`) |
| `{area}.internal.md` | the sensitive detail | no (`publish: false`) |

The redacted stub on the published side records **that** the fact exists and **which class** it belongs to, without disclosing it:

```markdown
- `security-07` — **[internal]** credential-handling detail recorded in `security.internal.md#security-07`
  - class: `secret-exposure` · where: `{path}` · observed: `2026-08-16`
```

A page may cite the stub — it may never cite, link or quote the internal file. That is checked by the exposure gate (📖 `08-verification-gates.md`).
